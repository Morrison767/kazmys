# МП Торгового Дома — прототип

Интерактивный прототип корпоративного маркетплейса закупки неосновных материалов
для ТОО «Корпорация Казахмыс» / Торговый Дом. Демонстрационный, без бэкенда:
роль переключается вручную в шапке, данные — локальные (в проде — D365 F&O, HR API, SMS-шлюз).

## Запуск

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # прод-сборка в dist/
npm run lint     # tsc --noEmit
```

## Стек

Vite 6 + React 18 + TypeScript, Tailwind CSS 3.4 (HSL-токены в CSS-переменных),
react-router-dom 6, zustand 5, lucide-react, clsx + tailwind-merge.

## Дизайн-система

Унаследована от проекта-донора `adata-tnved`:

- бренд-синий `--primary: 217 91% 55%` (≈ `#2474F5`), фон белый, текст `#0F172A`,
  границы `#E0E5EB`, активный пункт меню `--accent` (≈ `#DCEBFE`), `--radius: 12px`;
- семантика состояний поднята в токены: `success` / `warning` / `info` / `danger`
  (в доноре была ад-хок классами Tailwind);
- шрифт Open Sans, тайп-скейл на сетке 4px, минимум 12px;
- поверхности: `rounded-2xl border border-border bg-card p-6`, вложенные плитки
  `bg-muted/30`, тени преимущественно `shadow-sm`, всплывающее — `shadow-xl/2xl`.

Токены — [src/index.css](src/index.css), маппинг в Tailwind — [tailwind.config.ts](tailwind.config.ts).

## Демо-данные

[src/mocks/](src/mocks/) — 4 региона, 6 предприятий (одно вне D365 F&O), 4 РЕСХ,
7 цехов, трёхуровневый каталог (6 разделов → 18 групп → 53 вида) на 154 позиции,
7 поставщиков (договоры: действует / истекает / истёк / проект), 10 пользователей,
20 лимитов и 6 норм расхода, 19 заказов на всех статусах жизненного цикла,
архив перезаказов по 8 позициям инструмента.

**Каталог собран из реальной номенклатуры склада Казахмыса.** Источник —
[SMAT](https://smat.amvp.kz) (проект «СМАТ V2»: 173 574 позиции, разложенные
LLM по дереву 25 → 543 → 5 055). Из источника берутся структура категорий
и названия позиций; артикулы, коды номенклатуры, цены, единицы измерения,
остатки на РЕСХ и нормативные сроки службы генерируются — в источнике их нет,
а внутренние номенклатурные коды в репозиторий не переносятся.

Пересобрать каталог:

```bash
node scripts/import-smat.mjs      # выборка из API → data/smat-selection.json
node scripts/fetch-images.mjs     # фото с Wikimedia Commons → public/products
node scripts/generate-catalog.mjs # → src/mocks/categories.ts, products.ts
```

Фотографии есть у 12 позиций — свободные лицензии, атрибуция в
[public/products/ATTRIBUTION.md](public/products/ATTRIBUTION.md); у остальных
позиций иконка-плейсхолдер (в проде фото приходят из каталога поставщика).

Наборы согласованы не вручную, а выводятся: поставщик позиции — от категории
закупа; суммы заказа, маршрут согласования и ссылки на документы ERP — из позиций
и порогов лимитов; метрики ходимости — из архива перезаказов. Реэкспорт —
[src/mocks/index.ts](src/mocks/index.ts).

## Layout

Сайдбар слева на всю высоту (сворачивается в icon-rail 284px ↔ 80px), справа
шапка `h-16` + прокручиваемый `main`, контент центрируется по `max-w-content` (83rem).

На ширинах `< lg` (Этап 7) сайдбар и переключатель роли скрываются:

- навигация — [нижняя панель](src/components/layout/MobileNav.tsx): до трёх
  разделов роли плюс «Ещё» (у Заказчика это Каталог · Корзина · Заказы · Ещё);
- профиль, смена роли и остальные разделы — в шите
  [«Ещё»](src/components/layout/MoreSheet.tsx);
- корзина и карточка заказа получают sticky-панель основного действия
  ([CartCheckoutBar](src/components/catalog/CartCheckoutBar.tsx));
- виджет лимита, карточки товара, карточки согласования и состав заказа
  переключаются на компактные варианты (список вместо таблицы, кнопки на всю
  ширину);
- админ-панель и аналитика на мобильном скроллятся горизонтально — осознанный
  компромисс: это офисные разделы.

Разделы ТД (аналитика, админка) грузятся отдельными чанками с скелетоном
загрузки — основной бандл не тянет библиотеку графиков на телефон
(368 кБ против 821 кБ до разделения).

## Состояние

- `useSessionStore` — текущая роль и пользователь (в проде — HR API по ИИН + SMS-код);
- `useCartStore` — корзина, цех и РЕСХ доставки;
- `useOrdersStore` — заказы, переходы статусов с записью в историю;
- `useLimitsStore` — лимиты цехов по категориям и нормы расхода;
- `useCatalogStore` — категории, номенклатура, поставщики, оргструктура, склады.

На Этапе 0 хранилища пустые: mock-данные — Этап 1.

## Каталог

Дерево категорий — три уровня: **раздел** (категория закупа: рамочный договор,
лимит цеха, доступ по типу товара) → **группа** → **вид**. Позиции привязаны
к видам. В каталоге дерево открывается кнопкой «Категории»
([CategoryTreeDropdown](src/components/catalog/CategoryTreeDropdown.tsx)):
панель поверх контента, раскрытие ветвей, «Развернуть всё / Свернуть всё»
и число доступных цеху позиций справа от каждой ветки.

## Логика заказа (Этап 2)

Проверка лимитов — [src/lib/cart-limits.ts](src/lib/cart-limits.ts): корзина
разбивается по категориям закупа, каждая проверяется своим лимитом цеха,
итоговый вердикт — самый строгий:

| Вердикт | Условие | Что происходит |
|---|---|---|
| `auto` | сумма заказа по категории ≤ порога авто-одобрения, лимит периода не исчерпан | заказ создаётся со статусом «Согласован» |
| `approval` | сумма выше порога, но лимит цеха не превышен | статус «На согласовании»; выше порога эскалации в маршрут добавляются руководитель подразделения и бюджетный контролёр |
| `exceeded` | факт + корзина выходит за лимит суммы или норму количества | оформление заблокировано |
| `not_allowed` | категория не открыта цеху | оформление заблокировано |

Оформление — [src/lib/create-order.ts](src/lib/create-order.ts): номер заказа
продолжает нумерацию demo-данных, цены фиксируются на момент оформления,
для предприятий вне D365 F&O заказ помечается `erp.isOutsideErp`.
Оформленный заказ сразу уменьшает доступный лимит цеха
(`useLimitsStore.registerUsage`).

## Согласование (Этап 3)

Переходы статусов — чистые функции в
[src/lib/approve-order.ts](src/lib/approve-order.ts), хранилище только
подменяет заказ (`useOrdersStore.updateOrder`):

- `applyApproval` — «Согласован», отметки в маршруте согласования, запись
  в историю; при подтверждении повышенного порога закрываются также шаги
  руководителя подразделения и бюджетного контролёра;
- `applyRejection` — «Отклонён» с обязательным комментарием (в `rejectionReason`
  и в истории статусов);
- `applyErpTransfer` — «Передан в ERP» с номером Purchase Requisition
  и привязкой к рамочному договору; идемпотентна и не применяется к заказам
  предприятий вне D365 F&O (для них «Согласован» — финал упрощённого пути).

Область видимости и фильтры списка — [src/lib/order-scope.ts](src/lib/order-scope.ts).
Уведомления — [useToastsStore](src/store/toasts.ts) + [ToastViewport](src/components/ui/Toast.tsx).

## Трекер заказа (Этап 4)

Модель трекера — [src/config/order-stepper.ts](src/config/order-stepper.ts).
Вариант пути выбирается по признаку предприятия (`Order.erp.isOutsideErp`,
источник — `Enterprise.erp` в демо-данных):

- **Полный путь** (D365 F&O), 7 шагов: Оформлен → На согласовании → Согласован →
  Передан в ERP → У поставщика → На РЕСХ / в пути на предприятие → Получен.
  У трёх ERP-шагов — своя подсказка «i» о том, что стоит за шагом в реальной системе.
- **Короткий путь** (вне D365 F&O), 4 шага: Оформлен → На согласовании →
  Согласован → Получен. ERP-шагов нет; отгрузка поставщиком показывается
  подстатусом внутри шага «Согласован».

Один визуальный шаг может покрывать несколько статусов enum (например,
«На РЕСХ / в пути» — это `AtWarehouse` и `InTransit`), поэтому данные ERP
не теряются, а трекер остаётся читаемым. Цвет активного шага берётся из того же
`ORDER_STATUS_META`, что и Badge в списке заказов.

Переходы конвейера — [src/lib/advance-order.ts](src/lib/advance-order.ts):
`advanceOrder` (один шаг вперёд, с созданием PO и документа перемещения),
`confirmReceiptFromCurrentStep` (подтверждение получения человеком; если
перемещение РЕСХ → предприятие ещё не зафиксировано, оно дописывается).
Кнопка «Симулировать следующий шаг» — только демо, вынесена в отдельный блок
«Демо-инструменты»; решение согласующего и подтверждение получения она
не подменяет.

## Админ-панель ТД (Этап 5)

Все три страницы правят те же объекты в общем состоянии, что использует
потребительская часть, — отдельных копий данных нет:

| Страница | Что меняет | Где сразу видно |
|---|---|---|
| `/admin/catalog` | `Product` (добавление, правка, `isArchived`) | каталог заказчика скрывает позицию |
| `/admin/catalog` → матрица доступа | `Workshop.allowedCategoryIds` | категории в каталоге цеха, проверка лимитов в корзине |
| `/admin/limits` | `Limit.amountLimit` / `autoApprovalThreshold` / `escalationThreshold` | вердикт корзины (Этап 2) и маршрут согласования (Этап 3) |

## Аналитика (Этап 6)

Все показатели считаются на лету из общего состояния —
[src/lib/analytics.ts](src/lib/analytics.ts), «нарисованных» констант нет:

- **KPI**: объём закупок (по заказам, кроме черновиков и отклонённых),
  исполнение бюджета (сумма факта / сумма лимитов), средний срок поставки
  («Согласован» → «Получен»), число аномалий;
- **Оперативная аналитика**: объём по месяцам и категориям (recharts,
  стек с зазором в цвет поверхности + та же таблица чисел), исполнение бюджета
  по цехам с прогнозом исчерпания (`остаток / средний расход в день`, при нулевом
  расходе — «Не исчерпается при текущем темпе»), сроки поставки против
  `Supplier.normativeDeliveryDays`, топ-10 позиций со спарклайном;
- **Ходимость инструмента**: интервалы перезаказов считаются по датам архива,
  подсветка при интервале < 70% нормативного срока, сортировка «худшие сверху»;
- **Аномалии**: рост числа заказов позиции цехом более чем в 1,5 раза
  за последние 90 дней против предыдущих 90. `detectAnomalies` — единственный
  расчёт, он же питает KPI-карточку, поэтому счётчик сверху и число карточек
  всегда совпадают. Кнопка «Проверить заказы» ведёт на
  `/orders?workshop=…&product=…`.

Палитра графиков — [src/config/chart-theme.ts](src/config/chart-theme.ts):
фиксированный порядок цветов по категории (фильтр не перекрашивает серии),
набор проверен на различимость при дальтонизме и контраст к фону.

Поставщик позиции не выбирается вручную, а выводится от категории закупа
([admin-drafts.ts](src/lib/admin-drafts.ts)) — модель «один поставщик
на категорию» нельзя нарушить из интерфейса. Состояние договора считается
от срока действия ([supplier-contract.ts](src/lib/supplier-contract.ts)),
метрики поставщика — по заказам из общего состояния
([supplier-metrics.ts](src/lib/supplier-metrics.ts)); средний срок поставки
показывается только при двух и более завершённых поставках, иначе —
«Недостаточно данных».
